# Secure Coding Guidelines: Session Management

## 1. Purpose and Scope

This section establishes requirements for managing user sessions in web and API applications. Session management is the mechanism by which a successful authentication is bound to subsequent requests; weakness in session handling effectively voids authentication. This guideline covers session identifier generation, storage, transmission, lifetime, and termination.

These guidelines map to OWASP ASVS V3 (Session Management), OWASP Top 10 2021 A07, PCI DSS 4.0 Requirements 8.2.8 and 8.3.10, HIPAA §164.312(a)(2)(iii) (Automatic Logoff), NIST SP 800-63B Section 7, and CWE-384, CWE-613, CWE-614, CWE-1004.

## 2. General Principles

A session identifier is a bearer token: possession alone grants access. Session identifiers shall be unpredictable, long enough to resist brute force, transmitted only over authenticated encrypted channels, scoped narrowly, and invalidated promptly when no longer needed.

Stateful sessions stored server-side are preferred over self-contained tokens (JWT) for browser-facing applications, because server-side sessions can be revoked immediately. Where self-contained tokens are used, a complementary revocation mechanism shall be implemented.

## 3. Normative Requirements

Session identifiers shall be generated by a cryptographically secure random number generator and shall contain at least 128 bits of entropy (NIST SP 800-63B Section 7.1.1). Sequential, predictable, or user-derived identifiers are prohibited.

Session identifiers in browser contexts shall be transmitted via cookies with the following attributes: `Secure` (always, with no exception for development environments that handle real credentials), `HttpOnly` (unless the application has a specific documented need for JavaScript access), `SameSite=Lax` (or `Strict` for sensitive applications), and either `__Host-` or `__Secure-` prefix where applicable. The cookie shall have an explicit `Path` and shall not have a broad `Domain` attribute.

A new session identifier shall be issued upon authentication. Pre-authentication session identifiers shall not be reused post-authentication (defense against session fixation, CWE-384). The same applies to any privilege escalation event.

Absolute session lifetime shall not exceed 24 hours for standard applications and shall be substantially shorter (typically 15 minutes of inactivity, 8 hours absolute) for systems handling cardholder data or PHI. Idle timeout shall be enforced server-side; client-side timeout is informational only.

Logout shall invalidate the session server-side immediately, not merely clear the client-side cookie. Concurrent session policies shall be documented and enforced where required.

For API authentication using bearer tokens, tokens shall have short lifetimes (typically 15 minutes for access tokens) with refresh tokens used for renewal. Refresh tokens shall be rotated on each use and shall be revocable.

CSRF protection shall be implemented for all state-changing endpoints in browser contexts via synchronizer tokens, double-submit cookies, or `SameSite` cookie attribute combined with origin checking.

## 4. Language-Specific Guidance

### 4.1 Java

Use the framework's session management: Spring Session with Redis or JDBC backing, or the servlet container's session implementation. Configure `server.servlet.session.cookie.secure=true`, `http-only=true`, `same-site=lax`, and a documented `max-age`.

On authentication success, invalidate the existing session and create a new one:

~~~java
HttpSession oldSession = request.getSession(false);
if (oldSession != null) oldSession.invalidate();
HttpSession newSession = request.getSession(true);
// migrate any needed attributes explicitly
~~~

For Spring Security, this is handled automatically by `SessionFixationProtectionStrategy` when configured (`sessionManagement().sessionFixation().migrateSession()`).

For CSRF, enable Spring Security's CSRF protection (`CookieCsrfTokenRepository.withHttpOnlyFalse()` for SPA double-submit, or default session-backed token).

For JWT-based APIs, use short-lived access tokens (15 minutes) and store refresh tokens server-side with rotation. Validate `jti` against a denylist for revocation.

### 4.2 Python

For Django, configure `SESSION_COOKIE_SECURE=True`, `SESSION_COOKIE_HTTPONLY=True`, `SESSION_COOKIE_SAMESITE='Lax'`, and `SESSION_ENGINE='django.contrib.sessions.backends.cached_db'` (or signed cookies for stateless services with awareness of the revocation tradeoff). Django regenerates session keys on login by default; ensure `SESSION_COOKIE_AGE` is set appropriately.

For Flask, configure `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_HTTPONLY`, `SESSION_COOKIE_SAMESITE` in app config. Use server-side sessions (Flask-Session with Redis) rather than the default client-side signed cookies for any sensitive application.

For FastAPI, use a vetted session middleware or implement session storage in Redis. The `SessionMiddleware` from Starlette uses signed cookies; for sensitive data, use a server-side store keyed by an opaque session ID.

For CSRF in Django, the built-in middleware is sufficient if not disabled. For Flask, use Flask-WTF or Flask-SeaSurf. For FastAPI, use `fastapi-csrf-protect` or implement explicit origin and token checks.

For JWT, use `pyjwt` with short expirations and maintain a revocation list keyed by `jti` in Redis with TTL matching token lifetime.

### 4.3 C

Session management in C is uncommon at the application level; it is typically delegated to a web server, reverse proxy, or framework written in another language. When implementing session management in a C-based service (a CGI handler or a libmicrohttpd application), generate session identifiers with `getrandom(2)` on Linux, `arc4random_buf` on BSD, or `RAND_bytes` from OpenSSL. Do not use `rand`, `random`, or time-based seeds.

Store sessions in an external store (Redis, Memcached, a database) accessed via vetted client libraries. Do not implement custom in-memory session tables in shared-state servers without careful concurrency control; the resulting bugs are typically use-after-free or time-of-check-time-of-use vulnerabilities.

Set cookie attributes explicitly in `Set-Cookie` headers and verify them with a tool such as `artais-cookie-cop` in CI.

### 4.4 C++

The C guidance applies. Use a C++ web framework (Crow, Drogon, Pistache) that provides session management primitives, and configure it explicitly rather than relying on defaults. Verify that the framework uses a CSPRNG for session ID generation.

For session storage, use a Redis client (`redis-plus-plus`, `cpp_redis`) or equivalent. Wrap session lifetime in RAII so that sessions are cleaned up on exit paths including exceptions.

## 5. Verification

Verify session cookie attributes with `artais-cookie-cop`. Static analysis shall flag use of non-cryptographic RNGs for session IDs. Dynamic testing shall verify session fixation protection, idle and absolute timeout enforcement, and logout effectiveness. CSRF protections shall be tested on all state-changing endpoints. Penetration testing shall include session hijacking, fixation, and replay attempts.
