# Secure Coding Guidelines: Software Bill of Materials (SBOM)

## 1. Purpose and Scope

This section establishes requirements for generating, distributing, and consuming Software Bill of Materials (SBOM) documents for applications and infrastructure components developed or maintained by Artais Security. An SBOM is a formal, machine-readable inventory of components that make up a piece of software. SBOMs enable rapid vulnerability assessment, license compliance, and supply chain risk analysis.

These guidelines map to NIST SP 800-218 (SSDF), Executive Order 14028 (Improving the Nation's Cybersecurity), CISA SBOM minimum elements, and OWASP CycloneDX and SPDX specifications.

## 2. General Principles

Every artifact released by the organization shall have a corresponding SBOM. SBOMs shall be generated by the build process from authoritative inputs (lockfiles, container manifests), not produced manually after the fact.

SBOMs shall be available alongside the artifacts they describe, with a documented retrieval mechanism. Consumers of the artifacts (including downstream teams within the organization) shall be able to discover and consume SBOMs without ad-hoc requests.

## 3. Normative Requirements

### Format

SBOMs shall be produced in one of the standard formats: CycloneDX (preferred for the security use case due to broader vulnerability and VEX support) or SPDX (preferred for license compliance use case). Multiple formats may be produced from the same source data.

The SBOM format version shall be current; SPDX 2.3 or 3.x and CycloneDX 1.4 or later are appropriate at the time of writing.

### Minimum Content

SBOMs shall include, per CISA minimum elements:

- Author of SBOM
- Supplier name
- Component name
- Component version
- Other component unique identifiers (PURL, CPE, hash)
- Dependency relationships
- Timestamp

For each component, package URL (PURL) shall be the primary identifier. PURLs uniquely identify package-manager-distributed software (`pkg:npm/lodash@4.17.21`, `pkg:pypi/requests@2.31.0`).

Hashes (SHA-256 minimum) shall be included where available.

License information shall be included for license compliance use cases (SPDX preferred).

### Generation

SBOMs shall be generated at build time from build inputs. Build tools that natively produce SBOMs (or have plugins) shall be used:

- `syft` for filesystem and container scanning.
- `cyclonedx-bom-maven-plugin`, `cyclonedx-gradle-plugin` for Java.
- `cyclonedx-python` for Python.
- `cyclonedx-npm` for Node.js.
- `cyclonedx-go` for Go.
- `cargo-cyclonedx` for Rust.

For containers, the SBOM shall describe both the application contents and the base image layers. `syft` produces this from container images directly.

For multi-component releases, a top-level SBOM shall reference per-component SBOMs (CycloneDX `externalReferences` or SPDX `Relationships`).

### Distribution

SBOMs shall be published with the artifact:

- For container images, attached as an artifact in the registry (OCI SBOM attestation, Sigstore Cosign).
- For Maven artifacts, published alongside the JAR (`-sbom.json` classifier or in the metadata).
- For Python wheels, published as a metadata file in the distribution.
- For releases, attached to the release artifact (GitHub release asset, S3 bucket).

Internal SBOMs shall be accessible to security and engineering teams via a documented mechanism.

### Signing and Attestation

SBOMs shall be signed by the build system. The signature shall be verifiable by consumers. Sigstore Cosign with keyless signing is the current preferred mechanism for OCI artifacts.

SLSA provenance attestation (build environment, source commit, builder identity) shall accompany SBOMs for high-assurance artifacts.

### Consumption

The organization shall maintain an inventory of SBOMs for all deployed software, both internally developed and externally acquired. The inventory shall be queryable for vulnerability response.

For each deployed system, the SBOM shall be loaded into a dependency tracker (OWASP Dependency-Track, GUAC) that monitors against the NVD and KEV catalog and alerts on newly disclosed vulnerabilities affecting components in use.

### VEX

Where SBOMs include components with known vulnerabilities that do not apply to the application's use of the component, a Vulnerability Exploitability eXchange (VEX) document shall accompany the SBOM. VEX statements (CycloneDX VEX, OpenVEX, CSAF VEX) declare component vulnerabilities as not_affected, affected, fixed, or under_investigation with justification.

### Lifecycle

SBOMs shall be regenerated on every release. Modifications to deployed software (patches, hotfixes) shall produce updated SBOMs.

SBOMs for retired software shall be retained per the organization's record retention policy and shall remain accessible for incident response affecting historical deployments.

## 4. Language-Specific Guidance

### 4.1 Java

For Maven, add the CycloneDX plugin:

~~~xml
<plugin>
    <groupId>org.cyclonedx</groupId>
    <artifactId>cyclonedx-maven-plugin</artifactId>
    <version>2.7.10</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals><goal>makeAggregateBom</goal></goals>
        </execution>
    </executions>
</plugin>
~~~

For Gradle, use `org.cyclonedx.bom`:

~~~groovy
plugins { id 'org.cyclonedx.bom' version '1.8.2' }
cyclonedxBom { outputFormat = "json"; schemaVersion = "1.5" }
~~~

For container images, run `syft` against the produced image and store both the JAR-level and image-level SBOMs.

### 4.2 Python

Generate from the lockfile using `cyclonedx-py`:

~~~
cyclonedx-py poetry --output-format json --output-file sbom.json
~~~

Or use `pip-audit` which generates CycloneDX as a side effect of vulnerability scanning.

For containers, use `syft`:

~~~
syft packages docker:myapp:latest -o cyclonedx-json=sbom.json
~~~

For applications distributed as wheels, include a `pyproject.toml` build hook that generates the SBOM and packages it as a metadata file.

### 4.3 C

Generation from C builds depends on the build system:

- For Autoconf/Make projects, generate from the system package database (`dpkg-query`, `rpm -qa`) for dynamically-linked dependencies, plus a manual list of vendored sources.
- For CMake projects, the build can record dependencies via custom commands.
- `syft` against the produced binary or container provides a baseline.

For embedded firmware, the SBOM is typically constructed from the build manifest. Yocto, Buildroot, and similar produce manifests that can be transformed to CycloneDX.

### 4.4 C++

The C guidance applies. For `vcpkg` projects, `vcpkg-sbom` produces CycloneDX. For `conan` projects, `conan` 2.x has SBOM generation features.

`syft` against the binary or container is the cross-cutting approach when build-system support is incomplete.

## 5. Verification

CI shall fail if SBOM generation fails. SBOMs shall be validated against the format schema in CI. The SBOM inventory shall be reconciled with the artifact inventory periodically. Vulnerability monitoring shall produce alerts within 24 hours of NVD or KEV updates for components in the SBOM. SBOM signatures shall be verified on consumption. Annual review shall confirm SBOM completeness against deployed software.
